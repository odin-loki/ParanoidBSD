# PBSD agent execution: DeepSeek Flash only

Every task in PBSD is done by `deepseek-flash` (DeepSeek-V4.1-Flash) through the DeepSeek API. No other model, no IDE agents. The 40 work packages in `PBSD_PLAN.md` are broken into 12,963 atomic tasks in `tasks.yaml` / `tasks.json`.

## 1. Task breakdown

Each work package expands as:

1. `<WP>-IF` (decomposer): contract headers and stubs for the package. Depends on the frozen headers of upstream packages (`-IF` in phase 0, `-INT` afterwards).
2. For every reuse unit (one HBSD file, or one ~800-line slice of a Linux file or directory):
   - `-SPEC` decomposer: behaviour spec and contracts extracted from the source.
   - `-IMPL` implementer: port into the PBSD C++ dialect.
   - `-TEST` tester: unit and differential tests against the Linux/HBSD original (runs in parallel with IMPL).
   - `-PROOF` prover: drive PRISM until obligations close.
   - `-REVIEW` reviewer: a second, independent Flash agent checks the diff against the spec.
3. `<WP>-INT` integrator: merge all reviewed units into `pbsd-cutover` and run the package acceptance suite.

Sizing rule: a task's working set (role prompt + frozen contracts + source slice + its own diff) stays under 120k tokens with under 16k output per turn, so Flash finishes in at most 6 turns. A unit that breaks the rule is split by the decomposer into `-U###a`, `-U###b`, and so on.

## 2. Coordination: git plus a task database

Agents never talk free-form. They coordinate through three shared things:

1. **Frozen contracts**: `pbsd/kernel/include/**` after phase 0, read-only. Prompts embed the relevant headers verbatim (see caching).
2. **Task database** (SQLite to start, Postgres past ~500 workers): table `tasks` mirrors `tasks.yaml` plus `state, attempts, lease_until, worker, branch, last_error, artifacts`. States: `blocked → ready → leased → submitted → passed | failed → escalated`. The scheduler marks a task `ready` when all its `deps` are `passed`.
3. **Blackboard**: table `messages`, mirrored to `docs/plan/board/<task>.jsonl` on the branch. Typed messages only: `question` (to the unit's decomposer), `contract_change_request` (to the interface owner), `review_findings`, `test_failure`, `proof_failure`, `handoff`. A task reads every message addressed to it or its package when it starts.

Git: each task works on `t/<task-id>` cut from the latest `wp/<WP>`; the integrator merges into `wp/<WP>`, then into `pbsd-cutover`. Path ownership (`owns`) is enforced by a pre-merge hook. Units write one output file each, so merges inside a package do not conflict. Shared registration files (CMake lists, syscall tables, module tables) are generated by the integrator from per-unit fragments in `fragments/<task-id>.*`; nobody edits them by hand.

## 3. Roles

| Role | Does | Gate it must pass |
|---|---|---|
| decomposer | specs, contracts, splits oversize units, answers questions | reviewer approves spec; headers compile |
| implementer | writes C++ for one unit | build, dialect lint, sanitizers |
| tester | writes tests, runs them on reference and port | tests green on the reference first |
| prover | runs PRISM, adds invariants and lemmas | obligations closed or justified runtime checks |
| reviewer | independent review of the diff against the spec | structured approve or findings |
| integrator | merges, regenerates shared files, runs package suite | package acceptance criteria |

All roles are the same model (`deepseek-flash`) with different system prompts and tool sets. The scheduler, gates and merges are deterministic code, not agents.

## 4. Failure handling and escalation

- A failed gate posts a typed message and returns the task to `ready` with the error attached (attempt +1).
- Attempt 3 fails: rerun with a fresh context and a summary of every previous failure.
- Attempt 5 fails: a decomposer task splits it into smaller tasks, or files a `contract_change_request`.
- Contract change requests are batched per header. The owning decomposer applies them and bumps the header version; the scheduler re-queues dependants whose builds break.
- Attempt 8 fails, or a contract change is rejected twice: state `escalated` for Odin. The rest of the graph keeps running.
- Reviewer and implementer disagree twice: a third reviewer instance decides (majority of three).

## 5. Harness

- Plain Python with `asyncio` and `httpx` against the OpenAI-compatible endpoint `https://api.deepseek.com/chat/completions`, `model: "deepseek-flash"`. Thinking mode on for implementer, prover and reviewer; off for spec extraction and test boilerplate. Reuses the existing `pbsd.py` driver, `secrets/api-keys` and `docs/migration/*` bookkeeping.
- Tools via function calling: `read_file(path, range)`, `list_dir`, `grep`, `write_file(path, content)` (rejected outside `owns`), `apply_patch`, `build(target)`, `run_tests(filter)`, `run_prism(file)`, `post_message(to, type, body)`, `read_messages()`, `submit()`. Each task runs in its own container with its branch checked out.
- Concurrency: a semaphore at 2,400 in-flight requests (100 spare under the 2,500 limit); exponential backoff on 429 and 5xx; 30-minute leases so a dead worker's task is re-queued.
- Build, test and PRISM capacity is the real bottleneck: size the builder farm so a `build` call waits under ~60 s, and share object caches (sccache) keyed on contract version.
- Every response's `usage` block goes to `cost.jsonl` (hit, miss, output tokens, peak flag) for live cost tracking.

### Cache strategy

DeepSeek bills an identical prompt prefix at the cache-hit rate (50x cheaper). Every request is laid out in this order:

1. Global prefix, identical for every agent: dialect rules, naming rules, tool schemas.
2. Role prefix, identical per role.
3. Package prefix: frozen contract headers for the package, sorted and byte-stable.
4. Unit prefix: the source slice being ported and its spec.
5. Variable tail: task instructions, messages, tool results.

Nothing that changes per task (ids, timestamps, attempt counts) goes above layer 5. The scheduler runs tasks of the same package back to back so layers 1–3 stay warm. Target hit rate is 75–85% of input tokens.

### Off-peak scheduling

Peak is 01:00–04:00 and 06:00–10:00 UTC Monday to Friday (12:00–15:00 and 17:00–21:00 Sydney summer time). The scheduler drops to 10% concurrency in peak windows (critical-path retries only) and runs flat out the rest of the time and all weekend, which keeps more than 95% of tokens at off-peak rates.

## 6. Prompt templates

Every request starts with the shared global prefix:

```text
You are one agent in the PBSD build. PBSD is a clean-slate verified C++23 kernel. Rules:
- Use only the PBSD kernel dialect: no raw owning pointers, no new/delete/malloc, contracts [[expects]] [[ensures]] [[invariant]] on every public function, typestate where a resource has states.
- Never invent names for components or subsystems; use plain descriptive names.
- Reuse Linux and HBSD code: keep algorithms and structure, change only what the dialect and capability model require.
- Edit only paths in your task's owns. Frozen headers in pbsd/kernel/include are read-only; propose changes with post_message(type=contract_change_request).
- Communicate only through post_message. Call submit() when your gate should pass.
```

Decomposer:
```text
Role: decomposer. Task {{id}}: {{title}}.
Read {{source}} and the frozen contracts above. Write docs/plan/specs/{{wp}}/{{unit}}.md with purpose, inputs, outputs, invariants, locking, error paths and every behaviour callers rely on. Write the C++ declarations with contracts. If the unit will not fit one implementer task (over ~800 lines of output), split it and post the new task ids.
Acceptance: {{accept}}
```

Implementer:
```text
Role: implementer. Task {{id}}: {{title}}.
Spec: {{spec}}. Port {{source}} into {{owns}} following the spec exactly and keeping the original algorithm. Call build(), fix every error and lint finding, then submit().
Acceptance: {{accept}}
```

Tester:
```text
Role: tester. Task {{id}}: {{title}}.
Write tests in {{owns}} from the spec. Each test must pass on the reference ({{source}} built by the differential harness) before it is run on the PBSD port. Cover every error path in the spec.
Acceptance: {{accept}}
```

Prover:
```text
Role: prover. Task {{id}}: {{title}}.
Call run_prism on the unit. For each open obligation add loop invariants, lemmas or tighter contracts in {{owns}}; never weaken a contract the spec requires. Obligations you cannot close become runtime checks, each with a one-line reason.
Acceptance: {{accept}}
```

Reviewer:
```text
Role: reviewer. Task {{id}}: {{title}}.
Compare the diff on {{branch}} with the spec and the original source. Reply with JSON {"verdict": "approve" | "changes", "findings": [{"file": "", "line": 0, "issue": ""}]}. Reject any change in behaviour the spec lists, any raw pointer, any edit outside owns, any invented component name.
```

Integrator:
```text
Role: integrator. Task {{id}}: {{title}}.
Merge every reviewed unit branch of {{wp}} into wp/{{wp}}, regenerate shared files from fragments/, run the package acceptance suite, then merge into pbsd-cutover. On conflict or failure post test_failure to the owning unit task and stop.
Acceptance: {{accept}}
```

## 7. Cost and timeline (Flash only)

Off-peak prices per 1M tokens: cache hit $0.003, cache miss $0.15, output $0.60. Peak is double.

Assumptions per task: 4 turns, 60k input per turn at 80% cache hit, 10k output per turn including thinking, 1.6x for retries.

- Input: 4 × 60k × 1.6 = 384k tokens → 307k hit ($0.001) + 77k miss ($0.012)
- Output: 4 × 10k × 1.6 = 64k tokens ($0.038)
- About $0.05 per task, about $650 for 12,963 tasks. Provers and big driver units run longer, so budget 3x: $1,500–2,500 off-peak in total, roughly double at peak. These are estimates; `cost.jsonl` gives the real figure after the first few hundred tasks.

Timeline (superseded by section 8, the PC run): the dependency graph is about 12 levels deep. With 2,400 requests in flight, the model work for one pass over every task is about 1–2 weeks. The real limits are build, test and PRISM capacity and tasks that fail repeatedly: expect 4–8 weeks to a first full integration on `pbsd-cutover`, and 3–6 months until the cutover acceptance matrix (real hardware, NT and Android personalities) is green.

## 8. Default schedule: Odin's PC, no time limit

PBSD runs only on Odin's PC, a Lenovo ThinkStation P920 with two Xeon Scalable CPUs (32 cores in total, two NUMA nodes) and one 4 TB HDD, using only the DeepSeek Flash API. There is no deadline: all 12,964 tasks run, every proof is a full proof and no driver is deferred. The `month1` and `priority` fields in `tasks.yaml` only set the order: the core and the common drivers first, then mlx5, ice, iwlwifi and drm/xe. ### 8.1 Memory

The P920 has 16 DDR4 DIMM slots: 8 per CPU, 6 channels per CPU. It takes DDR4-2666 or DDR4-2933 registered ECC memory (RDIMM or LRDIMM), up to 1 TB with 16 × 64 GB (Lenovo PSREF). It has no 24-slot option, and 16 is the balanced full population.

- Plan RAM is 16 × the new stick's capacity.
- With 16 × 32 GB (512 GB), everything runs in RAM. The task database, the git repository, worktrees, build directories, ccache and QEMU images live in tmpfs. The HDD holds only checkpoints, backups and compressed reference trees.
- With 16 × 64 GB (1 TB), the same layout runs with more PRISM memory.
- With the current 64 GB, the HDD layout in 8.2 applies.

### 8.2 Slots and NUMA

With 512 GB or more, the 32 cores are the limit, not RAM. Slots are pinned with `numactl` so each job uses the memory of its own socket.

| Slot | Count | Cores | RAM each | Node |
|---|---|---|---|---|
| Agents (wait on the API) | 48 | shared | 0.3 GB | any |
| Compile and unit tests | 12 | 1 | 2 GB | 0 |
| QEMU | 3 | 2 | 4 GB | 0 |
| PRISM | 6 (8 with 1 TB) | 2 | 12 GB (24 GB with 1 TB) | 1 |

**Fastest upgrade after RAM:** NVMe in one of the P920's two onboard M.2 slots for checkpoints and backups. With everything in RAM this matters much less.

## 9. Fault tolerance of the run

The PC can lose power, run out of memory or crash, and the API can fail. The run has to resume where it stopped and never redo or corrupt finished work.

- **Idempotent tasks.** A task's output is its branch `t/<id>` plus its status row. Rerunning a task starts again from the last commit on its branch. Gates are pure functions of the commit, so running a gate twice gives the same answer.
- **Task database durability.** SQLite in WAL mode with `synchronous=FULL`, or Postgres with its own write-ahead log. Each state change is one transaction, written before the action it records. An `events` table is an append-only log of every lease, submit, gate result and message.
- **Atomic commits.** Agents write into the tmpfs worktree. The harness commits and pushes to the bare repository only at the end of each turn, and a gate result is recorded only with the commit SHA it ran on. Bare repo writes use git's own atomic ref updates.
- **RAM-to-HDD checkpoints.** Every 10 minutes, and at every turn end, the harness commits each tmpfs worktree's work-in-progress to a `wip/<id>` ref on the HDD. It also saves each agent's conversation state (messages and tool results, so far) to `state/<id>.jsonl.zst`. After a crash, at most 10 minutes of work is lost per task.
- **Resume after crash, power loss or OOM.** On start, the scheduler:
  1. Marks every `leased` task whose lease has expired as `ready`.
  2. Rebuilds worktrees from `wip/<id>` refs.
  3. Reloads conversation state.
  4. Reruns `git fsck` on the bare repo and `PRAGMA integrity_check` on SQLite.
  5. Continues.

  A systemd unit (or rc.d script) starts the scheduler on boot.
- **API failures.**
  - Timeout per request: 15 minutes.
  - Retries with exponential backoff and jitter on 429, 5xx and network errors, up to 8 tries.
  - The client honours `Retry-After` headers.
  - A circuit breaker halves concurrency after 20 failures in a minute and backs off for 5 minutes.
  - A balance check stops the run cleanly when the API returns 402 (out of credit).
  - An optional second key is used only if the first is revoked.
- **Watchdogs.**
  - Agent turn with no progress for 20 minutes: kill and requeue.
  - Build over 30 minutes, test over 60 minutes, or proof over its budget: kill the job and record a timeout.
  - QEMU guest with no console output for 10 minutes: kill it.
- **Poison-task quarantine.** A task that crashes the harness, triggers OOM, or hits the watchdog 3 times goes to `quarantined`. It is not retried automatically. It appears in the daily escalation report with logs attached.
- **Memory-pressure throttling.** See 8.2 and the scheduler in `tools/pbsd_run.py`. The scheduler also sets an `oom_score_adj` so QEMU and PRISM jobs are killed before the database or git server.
- **Daily backup.** At 04:00 Sydney time, during the API pause: the database dump, the bare repo (`git bundle`) and the logs go to a second disk or a cloud bucket.

## Appendix A. One-day run (optional, 24 hours wall clock)

Goal: run all 12,964 tasks at once and finish with a first full merged build on `pbsd-cutover` within 24 hours. The flattened dependencies for this option are in `deps_one_day` in `tasks.yaml` / `tasks.json`, which also carry and a `turns_budget` per task.

### A.1 Flattened graph

- **Contracts burst (hours 0–2):** all 40 `<WP>-IF` tasks start at once with no dependencies on each other. Each writes its package headers and stubs against the package list in `PBSD_PLAN.md`. Then one `P0-FREEZE` task reconciles every cross-package mismatch, builds all headers together, links all stubs, and tags `contracts-v1`.
- **Speculative unit work (from hour 2):** every unit's `-SPEC`, `-IMPL` and `-TEST` start together right after the freeze, built against the frozen headers and stubs, not against each other's real code. IMPL works from the original source plus contracts; the spec is checked against it at review.
- **Pipelined gates:** `-PROOF` needs only that unit's `-IMPL`. `-REVIEW` needs the unit's four tasks. `<WP>-INT` needs that package's reviews. `P6-01-INT` needs every package merge. Package merges link against the other packages' stubs, so no package waits for another package's real code.
- **Contract changes during the day:** batched hourly into `contracts-v1.N`. Only dependants whose build breaks are re-queued.

### A.2 Critical path

| Step | Turn budget |
|---|---|
| Package contracts (`-IF`) | 6 |
| Freeze (`P0-FREEZE`) | 12 |
| Port (`-IMPL`) | 8 |
| Proof (`-PROOF`) | 8 |
| Review (`-REVIEW`) | 4 |
| Package merge (`-INT`) | 6 |
| Final merge (`P6-01-INT`) | 6 |
| **No-retry critical path** | **50 turns** |
| Two review fix cycles (+2 × 12) | 24 |
| Three final-merge fix rounds (+3 × 6) | 18 |
| **Planned critical path** | **92 turns** |

Turn latency: Flash in thinking mode at about 10k output tokens per turn takes about 2–3 minutes of generation, plus 1–2 minutes of build or test tool time, so budget 5 minutes per turn. That makes 50 turns about 4.2 hours and 92 turns about 7.7 hours. The remaining ~16 hours are buffer for the escalation chain (fresh-context retry, split) on slow tasks and for queueing at the build farm.

### A.3 Infrastructure

**API concurrency.** About 10,300 unit tasks (spec, port, test, then proof and review) are live in the busy middle hours. Each task alternates between a model call and tool time, about 50/50, so about 5,000–6,000 requests are in flight at peak. One DeepSeek key allows 2,500.
- Preferred: ask DeepSeek for a raised concurrency limit of 6,000 on one account before the run.
- Otherwise: three API keys at 2,400 each, with the scheduler pinning each package to one key so a package's cached prompt prefix stays on the same key. Confirm with DeepSeek that several keys are allowed for one project.

### A.5 What "done in a day" means

In the day:
- Every task either passed its gate or escalated.
- `pbsd-cutover` builds for amd64, arm64 and riscv64 and boots in QEMU.
- Every package acceptance suite that runs in QEMU is green: LTP, kyua, xfstests, liburing, blktests, packetdrill, binder selftests and virtio drivers.
- PRISM obligations are proved, or listed as runtime checks with a reason.

Not in the day:
- Real-hardware validation: GPUs, NICs, Wi-Fi, USB, IOMMU attack tests and the performance benchmarks against Linux.
- Full Wine conformance, Android CTS and Windows kernel-mode drivers. These suites need longer than the day; first results only.
- Long fuzzing campaigns (syzkaller needs days to weeks), and turning runtime-check obligations into proofs.
- Escalated tasks: expect 2–5%, about 250–650 tasks, for Odin to review the next day.
- The cutover merge to `main`. That is a separate decision after hardware validation.

## Appendix B. 7–14 day run on cloud machines

This option uses cloud machines and one API key.

### B.1 Rules

- **Off-peak only.** The scheduler stops leasing new requests at 00:55 UTC and 05:55 UTC on weekdays and starts again at 04:00 and 10:00 UTC. In-flight turns may finish. In Sydney time (AEDT) the pauses are 12:00–15:00 and 17:00–21:00 on weekdays. That gives 17 working hours per weekday and 24 on weekends, about 133 hours a week.
- **One API key.** No more than 600 tasks are active at once, which is about 300 requests in flight at 50% tool time. That is well under the 2,500 limit and leaves room for bursts to 1,000 active tasks during merges.
- **Gated dependencies, less rework** (`deps` in `tasks.yaml`; the one-day graph is kept as `deps_one_day`):
  - Packages run in phase waves, and each wave's contracts are proved out by the previous wave's merges. That catches contract changes early, when few tasks depend on them.
  - Each unit runs `-SPEC` first. Then `-IMPL` and `-TEST` run in parallel from the approved spec. Then `-PROOF`, then `-REVIEW`.
  - This cuts the speculative rework (about 30% of tokens) from the one-day plan.
- **Cache-friendly ordering.** Tasks of one package run back to back on the one key, so the contract prefix stays cached.

### B.2 Throughput

All 12,964 tasks take about 73,000 agent turns, including retries. At 5 minutes per turn that is about 6,100 agent-hours. With 600 tasks active, that is about 10 off-peak hours of pure model work. The schedule is set by waves, build and test time, proof time and fix rounds, not by the API. So the plan uses a small, steady farm and spends the calendar time on validation between waves.

### B.3 Infrastructure

| Pool | Sizing |
|---|---|
| Agent tool containers | 600 at 0.25 vCPU, 1 GB (150 vCPU) |
| Compile, with sccache on shared storage | 256 vCPU |
| PRISM | 512 vCPU |
| QEMU test farm (amd64, arm64, riscv64) | 64 VMs, 128 vCPU |
| Task database, git server, object storage | One 16 vCPU VM |
| **Total** | **About 1,050 vCPU**, for example eight 128-vCPU spot machines plus one small VM |

Git: per-task branches live on a modest self-hosted git server, which can be the same 16 vCPU VM. `wp/<WP>` and `pbsd-cutover` are pushed to GitHub after each package merge, which is about 40 pushes plus fix rounds over the run and well within GitHub limits. GitHub alone also works: at about 1,000 pushes a day it is usable but slower, so batch task branches into one push per package per hour.

Scale the farm down to about half between waves (days 12–14), and turn it off in peak pauses if the cloud bills by the minute.
